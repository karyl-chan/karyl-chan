# Plugin Admin is separated from plugin registration by who initiates the action

An operator's actions on a plugin — delete, config edit, feature toggle, scope approval — were each hand-sequenced inside a route handler, with nothing owning the sequence. The module that named itself the layer between routes and models held the plugin's own lifecycle *plus* four operator actions that had drifted in, so it was neither one thing nor the other. We split the seam by actor: `Plugin Admin` owns what an operator initiates, and the registry keeps what the plugin initiates. Spec of record: the consensus comment on issue #30.

## Decisions worth remembering

- **The membership rule is the actor, and only the actor.** Not "business logic", not "things routes shouldn't do" — those are judgement calls that decay, which is how four operator actions ended up inside plugin registration in the first place. Who initiates is answerable without opinion, and it is already enforced elsewhere in the code: the two route families' auth guards are perfectly disjoint (capability checks on one side, scope checks on the other, zero crossings).
- **Plugin Admin owns admin *reads* too, not just writes.** Assembling the admin plugin list from four sources inside a route is what makes an admin route depend on four modules. The cost is a few reads that start as thin pass-throughs; the benefit is that "an admin route depends on one module" is a property you can check rather than an aspiration.
- **Two error conventions coexist, deliberately.** Plugin Admin returns an Admin Refusal; the plugin-initiated side throws. The line is the same actor line: an operator's refusal is an expected outcome to display, a plugin's malformed manifest is a protocol violation. The reason to prefer a returned refusal *here* is specific — this work relocates dozens of status-code decisions out of handlers, and an exception is invisible to the type system, so a forgotten case would compile. Anyone finding two conventions and assuming someone forgot to unify them should read this bullet instead.
- **The two config-write paths converge on their front half only.** They share Config Intake; they do not share persistence. One writes a JSON document holding native types and then syncs feature commands and emits a Plugin Change; the other writes one string-valued row per key and then stamps a schema version and writes an audit entry. Merging the back halves would convert a subtle divergence into a mode flag — the same bug wearing a parameter.
- **Non-string config values are accepted on both paths.** The guild-feature path always coerced a JSON boolean or number; the plugin-level path rejected it. Widening is additive, so nothing that works stops working; narrowing would break unattended maintenance scripts that no test and no log will reveal. Documented caveat: per-key string storage cannot round-trip a native type, so acceptance is symmetric but verbatim return is not.
- **The plugin-facing RPC surface gets a different remedy on purpose.** Its pain is request parsing — 105 of the plugin system's 126 hand-rolled type checks are there — not scattered orchestration. That is Fastify schemas, with a schema error formatter preserving the existing error body, plus service extraction at the two places that hold real orchestration (guild-KV quota accounting, interaction defer/follow-up state) and nowhere else. Building modules where there is no orchestration would repeat the mistake this ADR exists to correct.

## Rejected alternatives

- **One module spanning both actors.** It would straddle two authentication schemes and two trust levels, and would have no rule for what belongs inside — the precise condition that produced the original mess.
- **Adding Plugin Admin beside the registry without moving the four operator actions out.** Two modules would then both claim the seat between routes and models; route tests would fake two things, and the next person would have no way to know where to add a fifth.
- **Excluding the RPC route family from the work.** Tempting, since the actor line puts it outside Plugin Admin — but its problems are real and deferring them to a ticket nobody opens is not a decision, it is an omission. It stays in scope with its own remedy.
- **Starting with the delete teardown and the config paths**, as the original issue proposed. Those are the two hardest slices: seven ordered steps with best-effort semantics, and a divergence requiring behaviour rulings. Beginning there means inventing the conventions and ruling on behaviour simultaneously, with no way to tell which one broke. The first increment is instead a pure move of four already-tested methods.
- **Faking Plugin Admin in route tests.** The dependency structure earns its keep by thinning routes and giving orchestration an owner; the testing benefit is that route tests fake *nothing* internal. A stub would only prove that a route called a stub — and 35 test files already drive real routes against a real database.
