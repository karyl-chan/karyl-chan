# Behavior 拆成觸發與動作；指令是一種觸發，不是範圍的實作手段

Behaviors 最初照早期 Discord bot 的思路設計：每個 behavior 掛在一個 scope tab 上，由 tab 決定「在哪裡、對誰」，slash 指令只是附加的觸發方式，被當成某個範圍的實作手段。但 slash 指令（Discord application command）的可見範圍由 Discord 決定，不是 bot：只能註冊為全域或指定伺服器，用 `contexts` / `integration_types` 限定使用情境；伺服器內的身分組與頻道限制由伺服器管理員在「伺服器設定 → 整合」設定，bot token 無法設定，私訊裡也沒有對應機制。結果是指定使用者、群組、頻道的 slash behavior 對所有人可見，只在執行時拒絕；訊息比對設在 `PrivateChannel` 永遠不會觸發（盤點見 #92）。我們改採 Discord 自己的分工 —— **提供者宣告能力，管理員決定在哪裡給誰用** —— 把 behavior 拆成觸發與動作兩半。

決定當下（2026-10-26）正式站只有三筆系統 behavior —— 與 bot 私訊的 `!login`、`!manual`（停用）、`!break` —— 沒有自訂 behavior、沒有 session、沒有群組成員、沒有分頁層級的權限，所以重新設計不需要背負資料遷移，只需保住 `!login`。

## 決定

- **Behavior 是一個觸發綁定一個動作。**
- **觸發只有兩種：**
  - **指令觸發**：behavior 本身註冊為一個 Discord application command。設定直接沿用 Discord 的觀念：名稱、說明、參數、註冊範圍（全域或指定伺服器）、安裝方式、可用情境、預設成員權限；存檔時以 Discord 的規則驗證。誰看得到、在哪能用，交給 Discord 與伺服器管理員 —— 看得到就能執行，karyl 不做執行時的對象或位置檢查；要不要服務這個使用者，由動作自己決定（例如登入動作檢查授權）。
  - **指令是容器，葉節點綁動作。** 指令是 Discord 註冊的單位，持有名稱、說明與所有可見性設定（註冊範圍、安裝方式、可用情境、預設成員權限）；每個葉節點是一個 behavior，有自己的路徑（空、子指令，或日後的群組/子指令）、說明、參數與一個動作。沒有子指令時就是單一指令；Discord 規定有子指令時根指令不能呼叫，所以根葉節點與子指令不並存。第一階段只支援子指令一層，路徑欄位預留群組。可見性只在指令層，想讓某個子指令只給特定對象，就拆成另一個指令。
  - **訊息觸發**：只能設在 bot 收得到訊息的地方 —— 與 bot 的私訊，或伺服器（全部伺服器、指定伺服器、指定頻道）。對象篩選（所有人、指定使用者、群組）只在與 bot 的私訊提供。
- **Admin UI 依「在哪裡能用」分成三區，由觸發設定推導，不另外儲存：**
  - **App 指令**：可用情境跨越多處，或開放使用者安裝的指令。
  - **與 bot 的私訊**：此處的訊息比對，以及只在 bot 私訊可用的指令。
  - **伺服器**：伺服器的訊息比對，以及只在伺服器可用的指令（指定頻道只有訊息比對）。
  
  在某一區新增時，只開放那一區能選的設定。`behavior_scope_tabs` 與分頁層級的 `behavior:<scopeKey>.manage` 權限一併移除，只留 `behavior.manage`。
- **管理員可選的動作來源是 webhook 與 plugin action**，兩者共用同一個回覆模型。內建動作只供系統指令使用，不出現在動作選單裡。
- **系統指令是固定列，目前只有登入。** 它不能新增、刪除或停用，只能改觸發方式：與 bot 私訊的訊息比對，或一個指令（可見性照指令觸發的規則設定，不能當自訂指令的子指令）。伺服器裡的訊息比對不能選，因為回覆會公開在頻道。換觸發方式時，新的觸發要先生效（指令先成功註冊到 Discord）才停用舊的；失敗就保留原本的，所以不會因為切換而把自己鎖在門外。系統列釘在它所屬分區的最上方，預設與正式站現況相同（與 bot 私訊的 `!login`）。
- **移除持續對話**（一次觸發後，後續訊息都轉給同一個動作的 session）與它的逃生口 `break`，**也移除 `manual`**。
- **Plugin action 與觸發面無關**：plugin 只宣告動作 —— 輸入、支援哪些觸發種類、每個綁定可以有的設定 —— 管理員決定把它綁到哪個觸發。
- **分兩階段做**：第一階段是觸發拆分、UI 分區、動作來源抽象（先做 webhook；內建只給系統指令）、共用回覆模型、移除持續對話與 `manual`；第二階段才是 plugin action（manifest 宣告、SDK、派送、admin UI）。

## 被否決的選項

- **維持現況，指令範圍由 scope tab 推導。** Discord 無法表達大多數 tab 的範圍，只能靠執行時拒絕來模擬；管理員在後台看到的，和使用者在 Discord 實際看到的不一致。
- **在 karyl 端模擬每個使用者的可見性**（例如替特定使用者動態註冊伺服器指令）。私訊沒有伺服器指令可用，而且每個伺服器每天只能建立 200 次指令。
- **用伺服器管理員的 OAuth token 讓 karyl 代管指令權限。** 需要每個伺服器的管理員另外授權，私訊依然無效；Discord 的「伺服器設定 → 整合」已經提供同樣的能力。
- **所有指令集中放在「App 指令」一區。** 最單純，但「只在 bot 私訊可用的指令」和「只在伺服器可用的指令」就跟同一處的訊息比對分開了，管理員要在兩個地方找同一個情境的東西。
- **保留持續對話，限定在與 bot 的私訊並以結束按鈕取代 `break`。** 它是舊設計裡最「早期 bot」的部分，正式站從未產生過 session，登入情境也用不到；之後有真實需求時，再以按鈕、modal 或討論串的現代做法設計。
- **一個葉節點觸發多個動作**（例如先通知 A 再回覆 B）。一次互動只有一個初始回覆，多個動作搶回覆時，誰回、順序與部分失敗都沒有直觀答案；需要附帶副作用時另做事件通知。
- **用選項值分流到不同動作**（例如 `/nas action:login`）。各動作的參數不同，子指令本來就是 Discord 為此設計的結構。
- **登入做成可綁到任意觸發的內建動作**，並保證至少一個啟用中的綁定。彈性較大，但需要額外的鎖死保護規則，管理員也要多理解一種動作；固定的系統列沿用現有後台的做法，只開放改觸發方式。代價是登入同時只能有一種觸發方式，也不能放在自訂指令底下當子指令。
- **保留 `manual`。** 它是為了讓使用者找到看不見的私訊指令；改成指令觸發後，Discord 的指令選單本身就會列出來。
- **`dm_behavior`：plugin 宣告綁在私訊上的 behavior。** 早期做過、後來移除：behaviors 規劃為不限於私訊，而 plugin 的能力綁死在私訊這個觸發面上，找不到乾淨的擴展方式。這正是 plugin action 必須與觸發面無關的原因。

## 後果

- 系統 behavior 目前在每次開機時自動補建；移除 `manual`、`break` 必須改程式，不能只刪資料。正式站的 `!login` 原樣保留為登入系統列的觸發方式。
- Track 3 `plugin_commands`（plugin 在 manifest 寫死註冊範圍等三個維度）與「指令觸發 + plugin action」**並存**：前者給想自己掌握指令體驗的 plugin，後者給可被管理員組合的能力。兩者共用 Discord 的指令命名空間，所以同一註冊範圍內的名稱衝突要在存檔與註冊時拒絕，不能讓後註冊的靜默覆蓋。
- 第二階段需要新版的 plugin 協定與 SDK，三個獨立 plugin repo 要跟著升級。

## Addendum (2026-11-10): plugin action dispatch

Owner 於 2026-11-10 裁示第二階段（plugin action）改為現在做（#127，取代 2026-11-05「先不做」），並回答了上面「plugin 只宣告動作」留下的兩個問題。實作見 #201（契約與 SDK）、#203（bot 端）。

- **派送方式**：Plugin Dispatch（ADR 0001）新增一種 `behavior_action` kind，指令觸發和訊息觸發都用它。payload 是該觸發的 webhook `_meta` 加上 `action_key`，並帶 #113 的 callback token；plugin 先回 2xx，再憑 token 經 `interactions.respond` / `followup` 回覆該次觸發，與延後回覆的 webhook receiver 走同一條路、同一個回覆模型。plugin 自己的 token 與 scope 不參與回覆。
- **授權**：這條路**不經過** Feature Reach 或 Guild Reach（kind 的 reach 為 `none`）—— 管理員把 action 綁到某個觸發，這個綁定本身就是授權；誰能觸發，照觸發的規則由 Discord 與管理員決定。因此不與 #129 的 plugin 元件授權模型耦合。
- **宣告**：plugin 在 manifest 宣告 `behavior_actions: [{ key, name, description }]`（plugin-wire V-09 ~ V-12）。管理員在 behavior 的動作裡選 plugin 和 action；存檔時驗證該 plugin 目前的 manifest 確實宣告了它，每次執行時再驗一次（plugin 可能已經拿掉）。綁定以 pluginKey 為鍵，plugin 重新註冊或重裝後仍有效。
- **第一版沒有每個綁定的設定值**：指令參數、訊息內容與擷取群組原樣轉給 plugin。上面「每個綁定可以有的設定」與「支援哪些觸發種類」留待日後有實際需求再加；目前每個 action 都可綁到兩種觸發。
- **失敗**：plugin 離線、尚未就緒、未安裝，或 manifest 已不再宣告該 action 時，不派送；使用者看到失敗訊息，投遞紀錄分別記為 `plugin_unavailable` / `action_undeclared`。派送被拒或逾時則撤銷 token、顯示失敗訊息，與 webhook 相同。
- Track 1（ADR 原「待決定」第 2 項）維持 2026-11-05 的結論：不處理。SDK 何時發版由 owner 決定。

## 補充（2026-11-10，#126）：第二種固定列「服務」

owner 在 #126 裁示（2026-11-10）：自架服務透過 karyl 登入，觸發沿用 behavior，behavior 除了「系統」再多一種特殊類型「服務」。

- **Service Behavior 是第二種固定列**，資料裡記為 `actionSource: service`（`serviceId` 指向它的服務）。它和系統登入列一樣不能新增、刪除、停用或改動作，只能換觸發，而且只有 bot owner 能換；換觸發走同一套流程（新的觸發先生效，失敗就保留原本的），可選與 bot 私訊的訊息比對或一個全域指令，伺服器裡的訊息比對一樣不能選。它隨服務新增與刪除，數量不限。
- `systemKey` 仍只代表登入；「固定列」的判斷是 `systemKey` 非空或 `actionSource: service`。
- 服務列的訊息觸發排在登入之前比對，所以多了一條鎖死保護：任何服務的觸發都不能吃掉登入自己的觸發，兩邊存檔時都檢查。
