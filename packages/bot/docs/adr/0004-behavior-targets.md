# 作用對象是 behaviors 的分組單位；群組有自己的列；「比對到就停」只在對象內生效

ADR 0003 之後，admin UI 依「在哪裡能用」把 behaviors 分成分區（App 指令、與 bot 的私訊、伺服器），「對誰」則只是與 bot 私訊的訊息觸發表單裡的幾個欄位：指定使用者要手打 Discord ID；群組是一個手打的名稱，要先存檔才能設成員，最後一個引用它的觸發改掉之後名單就被清掉（#137）。伺服器與頻道也要先有 behavior 才會出現在側邊欄。結果是設定對象很費力，也沒有地方能一眼看到「這個人、這個群組有哪些 behaviors」。

對管理員來說，下面這些其實是同一種東西 —— 一個 behavior 要作用在哪個**對象**上：

| 作用對象 | key |
|---|---|
| 全部伺服器 | `guild:all` |
| 指定伺服器 | `guild:<guildId>` |
| 指定頻道 | `channel:<guildId>:<channelId>` |
| 所有人與 bot 的私訊 | `bot_dm` |
| 某個群組的成員與 bot 的私訊 | `group:<name>` |
| 特定使用者與 bot 的私訊 | `user:<userId>` |

另外保留 `app`（App 指令），給可用情境跨越多處的指令。

## 決定

- **Behavior Target（作用對象）是 admin UI 的分組單位，取代 Behavior Section。** 一個 behavior 屬於剛好一個對象。訊息觸發的對象是它的位置；只有與 bot 私訊、對象不是所有人的觸發改歸到 `user:` / `group:`。指令沒有對象篩選（ADR 0003 不變），它的對象就是原本的分區，由可見性設定推導，只會是 `app`、`bot_dm`、`guild:all` 或 `guild:<id>`。
- **對象是分組，不是分流。** 一則訊息可能同時符合好幾個對象：某人的私訊同時符合 `bot_dm`、他自己的 `user:` 與他所屬的每個 `group:`；伺服器裡的訊息同時符合 `guild:all`、該伺服器與該頻道。每個符合的對象各自比對、各自回覆。
- **「比對到就停」只在同一個對象內生效。** 命中勾了停止的觸發後，只跳過同一個對象後面的觸發，其他對象照常比對。系統登入與服務列不變：命中後結束整個走訪。這讓每個對象成為獨立的清單，管理員排序時只需要看一個對象。
- **不擴大對象篩選的範圍。** 使用者與群組仍然只適用於與 bot 的私訊；伺服器裡的訊息觸發一律對所有人生效。六種對象因此剛好對應 `behavior_definitions` 既有的欄位，「誰會比對到」的規則與 model validator 都不動。
- **管理員建立的對象存在名冊 `behavior_targets`。** 指定伺服器、指定頻道、特定使用者、群組各有一列（`key` 唯一）；三個內建對象沒有列。名冊只記「有哪些對象」：
  - 沒有 behavior 的對象照樣列出，直到管理員刪除它。
  - 被 behavior 或私訊白名單用到的對象一定有列 —— 每次 behavior 寫入的 transaction 收尾時補上（`registerTargetsInUse`），所以沒有哪條寫入路徑需要記得這件事，UI 也不必區分「建立的」與「因為有人用才存在的」兩種項目。
  - 還有 behavior 屬於它、或（群組）還有私訊白名單引用它時，不能刪除（`target_in_use`）。
  - 不能改名或搬移，刪掉重建。
- **群組是有自己列的對象，取代 #137 的「只在被引用時存在」。** 群組名稱全域唯一，一個群組一份名單。有列就能設成員（不必先有觸發），名單留到群組被刪除為止；刪除群組時名單一起刪。私訊白名單（#157）照舊用群組名稱引用同一份名單。
- **`behavior_definitions` 的欄位仍是 runtime 唯一的依據，不加 `targetId` 外鍵。** behavior 屬於哪個對象由欄位推導（`messageTriggerTarget` / `behaviorSection`），和分區原本的做法一樣。

## 影響

- **不能用個人或群組的觸發蓋掉所有人的觸發。** 以前把某人專屬的 `!help` 排在前面並勾停止，所有人版本就不會觸發；現在兩個都會回覆。這是讓對象彼此獨立的代價。之後真的需要覆蓋，再替觸發加「全部停止」的選項。
- **既有設定的行為會變。** 靠停止擋掉其他對象觸發的設定，升級後會多觸發。`stopOnMatch` 預設關閉，只有手動勾過的才受影響；migration 017 把筆數記到 bot event log。
- **一則訊息可能執行較多動作。** 每個符合的對象最多各有一個停止觸發命中：伺服器訊息最多三個，私訊是兩個加上使用者所屬的群組數。它們依序在同一個對話鎖內執行，共用同一份限速額度（每頻道或每位使用者 5 次／10 秒），額度不調整。比對成本的上限不變：沒有命中的訊息本來就走完全部觸發。
- **服務用的群組不再自動清空。** 服務列的對象群組就是能登入那個服務的名單，只有 owner 能改。以前服務換掉群組或被刪除後，沒人用的名單會被清掉；現在名單留著，而且變回一般管理員可以編輯的群組。owner 之後再把服務指到這個群組時，成員可能已經不是當初那批人 —— 服務卡片在選群組時顯示成員名單，owner 選的當下看得到誰能登入。
- **回滾。** migration 017 的 down 會 drop 名冊表；舊版在下一次 behavior 寫入時會照 #137 清掉沒有觸發引用的名單，這一版保留下來的名單會消失。要完整還原得用部署前的 DB 快照。

## 被否決的選項

- **位置與對象分開呈現**（側邊欄保留位置分區，另外加一個使用者與群組的區塊；表單是位置、對象兩個下拉）。資料模型不變，但管理員要在兩個清單之間對照同一件事，「點一個對象看它所有的 behaviors」也得做成跨位置的篩選檢視。
- **把對象篩選擴到伺服器訊息觸發**（對象 = 位置 × 人）。對象的組合變成二維，側邊欄要列「某人在某伺服器」這類項目；matcher、validator 與觸發轉換都要改。現在沒有這個需求。
- **替 behavior 加 `targetId` 外鍵。** matcher 的熱路徑、四個 model validator、固定列的觸發切換與指令快照都直接搬動欄位；指令沒有對象篩選，外鍵對它們只能是 null 加推導；SQLite 可能在沒有外鍵檢查的情況下執行。換來的只有群組改名比較方便。
- **比對順序改成「越具體的對象先比對」**（使用者 → 群組 → 所有人），停止維持全域。能保留覆蓋的用法，但既有私訊觸發的實際順序會跟著變，而且伺服器那一側（全部伺服器、伺服器、頻道）沒有同樣直觀的具體程度。
- **停止維持全域，另外提供跨對象排序。** 不動 runtime，但 UI 要多一個「同位置的優先順序」的概念，而且伺服器類對象彼此的先後原本就不能調，兩邊的能力對不上。
- **使用者檢視也列出他透過群組得到的 behaviors。** 使用者對象的意思是「只針對這個人」；群組的 behaviors 不是針對單一使用者的，列進來反而讓「這裡的東西改了會影響誰」變得不清楚。
